骨架阶段踩到的两个坑（已在本次修掉，写进这里免得重犯）：

1. **apktool 的 `$` 资源名**：`res/drawable/$mtrl_checkbox_button_icon_*__N.xml` 等 **40 个文件** 用 `$` 开头，aapt2 直接报 `'$' is not a valid file-based resource name character`。处理：文件名 `$`→`_`，并把 `res/**/*.xml` + `values/public.xml` 里的引用同步改写（98 个文件命中）。
2. **multidex**：开 `isCoreLibraryDesugaringEnabled` 而不开 `multiDexEnabled` 时 AGP 直接失败（`In order to use core library desugaring, please enable multidex`）。

## 四、对阶段 2/3 的具体调整建议

### 调整 1｜库不进源码，走 Maven（最重要）

dex 里的库占比和对应依赖（阶段 2 落地时按 jadx 的 import 核对版本）：

| dex 内包 | 源文件数 | 替代 |
|---|---|---|
| `androidx/**` | 1663 | `androidx.appcompat / core-ktx / work-runtime / room-runtime / constraintlayout / recyclerview / lifecycle / fragment / viewpager2 / emoji2 / media3(?)` 等按需引入 |
| `com/google/**` | 119 | `com.google.android.material`、firebase-messaging、play-services-* |
| `okhttp3/**` | 131 | `com.squareup.okhttp3:okhttp` |
| `io/socket/**` | 31 | `io.socket:socket.io-client`（2.2 的 WS 上报就走这个） |
| `kotlin/**` | 21 | `org.jetbrains.kotlin:kotlin-stdlib` |
| `pub/devrel/**` | 18 | 广告 SDK（pub.devrel.easypermissions / easypermissions 混淆体），按需引入或删 |
| `android/**`（16） | 16 | 三方库自带的兼容 shim，一般也不进源码 |

只有 `p000`~`p119`（996 文件）+ `com/lite/cloudfinder/**`（44 文件）= **1040 个文件**需要进 `src/main/java`，其余 **1999 个文件**是库（3039 = 1040 + 1999）。

这样做的直接收益：javac 错误从 142 → **13 处量级**，`JADX WARN` 文件从 478 → 137，阶段 3 从 5~10 天压到 1~2 天。

代价：`res/` 里有 1663 个 androidx 库的资源副本（`$mtrl_*`、`avd_*` 那些）。引入真依赖后会和库自身资源 **重名冲突**，阶段 4 需要把库资源从 `res/` 里整批清掉（只留 app 自己的 `black_bg_loading.html`、图标、布局、i18n）。这一步不要提前做，等依赖进来再清，否则工程先跑不起来。

### 调整 2｜混淆包不用改名，先建 `p0xx` 映射表

jadx 已经把 120 个 Unicode 包压成 `p000`~`p119`，类名 `C0NNN`。比手工把 `ڝږ؁ڋ/ھ` 改成 `Perm` 省事得多。建议：

- 阶段 2 先出 `docs/2.3-mapping.md`，一行 `p0NN/C0NNN` ↔ 2.2 smali 路径 ↔ 业务含义（用 2.2 的 `HANDOFF` 第四节那张表对照）
- 只对**真正要改**的 30~50 个类做语义重命名，其余保持 `p0xx`，避免大面积重命名引入回归

### 调整 3｜枚举那 5 个文件走「重新 smali 化」而不是硬修

`Failed to restore enum class` 的产物里枚举常量顺序和构造器参数都可能错，硬修容易引入运行时行为漂移（这项目的枚举是给协议字段用的）。建议这 5 个文件从 `project-2.2/smali/` 直接读原逻辑手写回来，和 `ForegroundKeepAliveService` 那个未反编译方法一起，作为「smali 兜底清单」的初始两条。
