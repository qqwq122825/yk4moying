## 一、最重要的结论：架构路线必须走「全量源码」，不能只挂 AAR

阶段 1 报告建议「库走 Maven 依赖，只搬 1040 个业务文件」。实际做下去发现这条路走不通，原因是这个 APK 的 R8 **把库的类名也一起混淆了**：

```
androidx.activity.result.AbstractC0004      ← 真实的 ActivityResultCallerKt 之类被改名
kotlin.jvm.internal.AbstractC0176           ← 真实的 kotlin.jvm.internal.Lambda
androidx.constraintlayout.motion.widget.RunnableC0025
androidx.room.RunnableC0098
com.google.android.material.datepicker.ViewOnClickListenerC0131
```

业务代码（`p0xx`）里大量引用这些「库包名 + 混淆短名」。真实 AAR 里不存在这些名字，因此：

- **只挂 AAR**：引用全部报 `找不到符号`，而且 vendored 别名类一旦被拉进来，会跟 AAR 的基类发生**版本漂移**（`setException` protected、`FilterInputStream.in` protected、构造器签名不符…）。实测这条路是 **959 处错误**。
- **全量源码**（dex 里 3039 个类全部进 `app/src/main/java`，不挂任何 AAR）：同名同版本，`protected`/构造器问题全部消失。解析级错误只有 **122 处**。

**结论：路线 A 落地为准 —— 全量源码 + 自带 res + 不依赖 AAR。**
代价是工程里有 1983 个库类源码（`androidx/ kotlin/ okhttp3/ io/ com/google/ pub/`），相当于 vendored；换来的是零版本漂移、行为与 2.2.345 完全一致。

配套动作：

| 项 | 处理 |
|---|---|
| `values/attrs.xml` | 从 `project-2.2` 恢复（1247 个 attr 全部来自库，之前删掉了，全量源码模式下必须回来） |
| `values/public.xml` | 恢复（5363 行，固定原始资源 ID）。dex 里 vendored 的 `R` 类硬编码了原始 ID，public.xml 保证 aapt2 生成的 ID 与之逐一对齐 |
| `app/build.gradle.kts` 的 `implementation(...)` | 全部移除，只留 `coreLibraryDesugaring` |
| `android/*` 16 个平台 stub | 不引入（jadx 只给出 `NoClassDefFoundError` 空壳，平台类从 android.jar 取） |

## 二、这一轮实际做了什么

### 1. 业务代码修正（阶段 1 列的 7 个文件，全部修完）

| 文件 | 处理 |
|---|---|
| `p002/EnumC0219` | 按 smali `<clinit>` 重建：21 个常量 + `f898: SparseArray`（键 0..19 → 对应常量，`COMBINED` 不进表） |
| `p002/EnumC0220` | 同上：19 个常量 + `f900`，`NONE` 的整型值是 **-1** 不是 ordinal，键为 -1 |
| `p002/EnumC0222` | 6 个常量；原 `<clinit>` 里的 SparseArray 构造后被丢弃（R8 死代码），省略 |
| `p096/EnumC0919` | `COROUTINE_SUSPENDED / UNDECIDED / RESUMED`（kotlinx CoroutineSingletons） |
| `p108/EnumC0983` | `PUBLIC / PROTECTED / INTERNAL / PRIVATE`（kotlinx DescriptorVisibility） |
| `p060/C0622:51` | `?? arrayList;` → `java.util.List`（既接 `Collections.emptyList()` 也接 `ArrayList`） |
| `p079/C0725:393` | `?? r0 = zM1545` → `int r0 = zM1545 ? 1 : 0`；并把 `(r0 == true ? 1 : 0)` 还原成 smali 的 `or-int/lit8`（`r0 \|= 2`、`r0 \|= 4`） |

枚举重建用了脚本解析 smali `<clinit>`（`new-instance` → `const-string` → `invoke-direct(name,ordinal,value)` → `SparseArray.put`），把寄存性别名链也解开了，`p002` 两个 SparseArray 的键值映射是**逐条核对**的，不是猜的。

### 2. 反编译缺陷批量修复（新增工具链）

| 工具 | 作用 |
|---|---|
| `tools/decompile.sh` | jadx 全量反编译（8 秒） |
| `tools/fix-loop.sh` | 编译 → 抓错误 → 自动补齐/回滚源码 → 再编译的循环（v2 支持「找不到符号 / 程序包不存在 / 重复类」三类） |
| CFR 0.152 | jadx 处理不了的类换一个反编译器重来 |

**CFR 的正确用法**（踩过两个坑，记下来）：

```bash
# 错：单类文件模式，匿名内部类全部变成 new /* Unavailable Anonymous Inner Class!! */
java -jar cfr.jar --outputdir out --extraclasspath dir path/to/Foo.class

# 对：整包 + jarfilter，匿名内部类能正常还原
java -jar cfr.jar appcompat-1.6.1.jar --outputdir out \
     --jarfilter androidx.appcompat.widget.ActivityChooserView --silent true
```

用 CFR 重做了 19 个 jadx 弄坏的库类（`StaggeredGridLayoutManager`、`ConstraintWidgetContainer`、`Chain`、`Direct`、`ViewDragHelper`、`ActionMenuPresenter`、`AppCompatSpinner`、`ActivityChooserView`、`AppCompatDelegateImpl`、`WindowInsetsControllerCompat`、`InputConnectionCompat`、`NetworkState`、`Operation`、`Chip` 等），并**回滚**了 6 个被 CFR 误伤的 Kotlin `*Kt` 类（CFR 反编译 Kotlin 字节码很差，`OperationKt`、`WorkSpecDaoKt` 必须保留 jadx 版本）。

AAR 从 Google Maven 取（Maven Central 上没有 androidx 的 aar/sources）：

```
https://dl.google.com/dl/android/maven2/androidx/<group>/<artifact>/<ver>/<artifact>-<ver>.aar
constraintlayout-core 是纯 jar，同上路径 .jar
```

### 3. 平台类嵌套名修正

jadx 会把平台嵌套类写成 `android.accessibilityservice.AccessibilityService$TakeScreenshotCallback`（带 `$` 的二元名），javac 认不出来。已改成点号形式，涉及 `p087/C0830`、`p087/C0832`、`p086/C0796`（无障碍截屏回调），并删掉 jadx 生成的 `NoClassDefFoundError` 空壳。

**编译现状：解析级错误已清零，语义级错误 1918 处 / 518 个文件**（快照 `apk-project/2.3/scratch/remaining-errors.txt`，一行一处，带 `文件:行: 消息`）。

已完成的两轮批量修复：删掉 jadx 误加的 `@Override` **126 处**（2334 → 2208），再把 CFR 误加的
`ChipDrawable` / `ChipGroup` 两个 dex 里不存在的类删掉、恢复 `Chip.java` 的 jadx 版本并补 1 处 `??`
（2208 → 1918）。

> **重要经验：错误数会被少数坏文件放大，必须按文件修，不要按错误数修。**
> `ChipDrawable`（185 处）+ `ChipGroup`（47 处）两个 CFR 误加的文件就带来了 2000+ 处连锁错误；
> 删掉后直接掉到只剩 1 处。同理，`WorkSpec.java` 175 处、`p086/C0797` 89 处也是这种「单文件炸弹」，
> 修它们比修 700 个零散 `找不到符号` 更划算。

> 注意：Gradle 日志里 `N 个错误` 是分页的，别拿它当总数；以去重后的 2334 为准。

## 四、下一步的三条路（建议按顺序试）

### 4.0 先摘「单文件炸弹」

`WorkSpec`(175) / `C0797`(89) / `AbstractC0851`(38) / `C0281`(31) 四个文件占 333 处，且都是业务要用的类，
先啃它们，收益最高。

### 4.1 再做可脚本化的批量修复（预计砍掉 300~400 处）

```bash
# 已完成：删掉错误的 @Override（126 处）
# 待做：int→byte 强转（75 处，switch case 常量）
# 待做：boolean/int 混用（13~21 处，找 (x == true ? 1 : 0) 一类写法）
# 待做：Chip 里那类 int→Drawable 强转（13 处）
```

纯文本改写，写完用 `tools/fix-loop.sh` 验证不回归即可。

### 4.2 Kotlin 库换成「jar + 只保留 mangled 别名」

`okhttp3` / `androidx.work` / `androidx.room` / `androidx.lifecycle` / `io.socket` 这几套是 Kotlin 写的，jadx+CFR 的 Java 还原质量最差（WorkSpec 一个文件 175 处）。方案：

- 把它们改成 `app/libs/*.jar`（从 `/tmp/aars/*.jar` 或 Maven 取），删掉 vendored 的 `.java`
- **只保留**业务代码实际引用的 mangled 别名类源码（如 `androidx.room.RunnableC0098`）
- 这样能一次性消掉 `okhttp3` 215 + `io` 74 + 部分 `androidx.work/room/lifecycle`

风险：mangled 别名类会重新引入少量基类签名问题，需要逐条核对（阶段 1 报告里 `Application`/`Observable` 那类 protected 报错就是这么来的）。

### 4.3 业务包 `p0xx` 先收敛

业务包 538 处是**必须修**的（后续开发都在这里）。建议顺序：

1. 先修 `p086/C0797`（Firebase 消息处理，89 处）和 `p087/AbstractC0851`（无障碍注入，38 处）
2. 再按 `docs/2.3-mapping.md`（待产出）把要改的 30~50 个业务类做语义重命名，其余保持 `p0xx`
3. 里程碑仍是 `./gradlew assembleDebug` 首次成功；在成功之前不要动 `versionCode`

## 五、复现命令

```bash
cd apk-project/2.3
export JAVA_HOME="$PWD/../tools/jdk-17.0.20.1+1/Contents/Home"
export PATH="$JAVA_HOME/bin:$PATH"
export ANDROID_HOME="$PWD/../tools/android-sdk"

grep -oE '[0-9]+ 个错误' scratch/build.log | tail -1     # 分页数字，仅供粗看
```

去重统计（以这个为准）：

```python
import re
from collections import Counter
txt = open('scratch/build.log', encoding='utf-8', errors='replace').read().splitlines()
byloc = {}
for l in txt:
    m = re.match(r'.*/java/(\S+?\.java):(\d+): 错误: (.*)', l)
    if m:
        byloc.setdefault((m.group(1), int(m.group(2))), m.group(3))
print(len(byloc), 'sites')
Counter(byloc.values()).most_common(20)
```
