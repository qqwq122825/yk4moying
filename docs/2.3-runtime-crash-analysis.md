# 2.3 装机运行结果：资源 ID 不一致（架构级问题）

> 日期：2026-10-21
> 结论：**APK 能装、能启动，但启动即崩**；根因是「预编译 jar 里硬编码的资源 ID」与「AGP 重新生成的资源 ID」不一致。
> 这是混合模式（jar + 源码）的固有缺陷，不是某个类的 bug。

---

## 一、装机链路已打通

| 步骤 | 结果 |
|---|---|
| 卸载旧 2.2（设备管理员） | 关无障碍 → `pm disable-user` → `uninstall` 成功 |
| 安装 2.3 | `Success`，versionCode 345 |
| 启动 | `am start -n com.lite.cloudfinder/com.lite.cloudfinder.activity.AliasS` 成功（**无报错**） |
| 进程 | 起来后立即崩（见下） |

> 中途踩的坑：设备上残留过 `pm disable-user` 后的坏包记录，导致一段时间内**所有**第三方包都报
> `START_CLASS_NOT_FOUND`（连 Telegram、11KB 的安装器 APK 都启动不了）。彻底 `uninstall` 干净后恢复正常。
> 排查结论：系统应用（Chrome/Play/相机）能启动，说明设备本身没坏。

## 二、崩溃与根因

```
FATAL EXCEPTION: main
Process: com.lite.cloudfinder
java.lang.RuntimeException: Unable to get provider androidx.startup.InitializationProvider:
    android.content.res.Resources$NotFoundException: String resource ID #0x7f10001d
  at androidx.startup.AppInitializer.discoverAndInitialize
  at androidx.startup.InitializationProvider.onCreate
```

`androidx.startup` 用**硬编码的 int** 去取 `R.string.androidx_startup`。查两个包的资源表：

| | 原始 2.2 APK | 我们的 2.3 APK |
|---|---|---|
| `0x7f10001d` | `string/androidx_startup` | `style/Base.TextAppearance.AppCompat.Caption` |
| `string/app_name` | `0x7f10001e` | `0x7f0f001e` |
| 资源表 PUBLIC 标记 | 5320 个 | **0 个** |

→ `res/values/public.xml`（从 apktool 还原、539 行、用于固定原始 ID）**AGP 8 在 application 模块里直接忽略**，
所以我们的 `resources.arsc` 是**全新分配的一套 ID**。

### 为什么这会致命

- 我们自己编译的源码：`R.xxx` 由 AGP 生成，和新的 arsc 一致 ✅
- `app/libs/moying-libs.jar` 里的类（来自原 dex 的预编译字节码）：资源 ID 是**烘焙进字节码的旧 ID** ❌

只要 jar 里的类碰资源（`androidx.startup`、`appcompat` 主题、`NotificationCompat` 的图标…），必然崩。

**混合模式（jar + 源码）在资源层面不可能自洽**：要么全部走源码（AGP 统一生成 R），要么全部走预编译 dex（沿用原 arsc）。这是这次踩到的最硬的结论。

## 三、两条出路

### 路线 A：全量源码 vendored（推荐）

把 2000 个库类也还原成 jadx 源码，删掉 jar。R 全部由 AGP 生成 → 资源 ID 全链路一致。

- 代价：回到我们阶段 2 面对过的「库内反编译瑕疵」，当时是 1918 处；但现在手上有三个自动修复器
  （`fix-uninit` / `fix-exceptions` / `fix-structure`）+ `ReflectUtil` 反射桥，且已验证能把业务侧 959 处干到 0。
- 预估：库侧 ~1900 处，其中 80% 是「变量未初始化 / 受检异常 / 不可达语句」这三类纯机械问题，脚本能吃掉。

### 路线 B：沿用预编译 dex（回到 apktool 路线，但业务码用源码）

保留原 `resources.arsc` + 原 dex 里的库类，只把**业务包**（`p0xx` + `com.lite`）用源码编译出的 dex 替换进去。

- 优点：资源 ID 天然一致，改动面最小
- 缺点：需要把「源码编译出的业务 dex」与原 dex 做**类替换合并**（dexlib2 脚本），构建链比 Gradle 原生复杂；
  且 `project-2.2` 那套 apktool 流程本来就能干这事（也许直接用 `build.sh` 更快）

### 路线 C（临时验证用）：绕开资源依赖

把 `androidx.startup` 的 provider 从清单里删掉，看下一个崩在哪里。**只适合探雷，不是办法**——
appcompat 主题、通知图标、WebView 页面都会继续踩。

## 四、当前状态

```
2.3 工程：编得过、装得上、启动即崩（资源 ID 不一致）
project-2.2：零改动，仍是可用的 2.2 基线
```

## 五、建议

按路线 A 推进：把 vendored 集合从「71 个类」扩到「全部库类」，删 jar，然后用现有脚本群把库侧错误刷下去。
这是唯一能让 R 自洽、且不需要维护两套构建链的路。
