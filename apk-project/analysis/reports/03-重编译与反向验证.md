# 03 · 反编译、重编译与反向验证

本文件记录“把 APK 完整还原成可编译源码 → 重新编译成 APK → 用独立手段证明还原无损”的完整过程与证据。

---

## 1. 工具链

宿主机原本没有 JDK，本次全部就地下载（无系统级安装，均在工程目录内）：

| 组件 | 版本 | 用途 | 位置 |
|---|---|---|---|
| Temurin JRE | 17.0.20.1+1 | 运行 apktool / jadx / apk 签名器 | `tools/jre/jdk-17.0.20.1+1-jre/bin/java.exe` |
| Apktool | 3.0.3 | DEX↔Smali、资源解码/回编（aapt2） | `tools/apktool.jar` |
| jadx | 1.5.6 | DEX→Java 反编译 | `tools/jadx/` |
| uber-apk-signer | 1.3.0 | zipalign + v1/v2/v3 签名与验签 | `tools/uber-apk-signer.jar` |

## 2. 反编译（两条独立通路）

```powershell
# 通路 A：Smali 级（可回编）——资源、Manifest、5,844 个 .smali
java -jar tools\apktool.jar d -f --no-debug-info -o apktool_out a0dcf711.zip

# 通路 B：Java 级（可读）——3,039 个 .java / 19.6 MB
java -Xmx4g -cp "tools\jadx\lib\*" jadx.cli.JadxCLI --threads-count 4 -d jadx_src a0dcf711.zip
```

结果：

| 通路 | 产物 | 数量 |
|---|---|---|
| apktool | `apktool_out/smali/**/*.smali` | **5,844**（与 DEX class_defs 数一致） |
| apktool | `apktool_out/AndroidManifest.xml`（明文） | 32,103 字节 |
| apktool | `res/`（obfuscated 资源名已按资源表恢复语义名） | 1,178 个文件 |
| jadx | `jadx_src/sources/**/*.java` | **3,039**（含 5,844 类 + 内部/匿名类） |

jadx 报告 21 条 *resource* 解码错误（某个被刻意破坏的 ZIP 资源条目），**不影响任何代码类**：5,844 个类全部反编译成功（`classes.dex` 无 multi-dex）。

> 混淆说明：R8 把远控核心类重命名为阿拉伯/叙利亚字母（如 `ڜٟٱڀ/ش`），jadx 将其映射为 `pNNN/Cmmmm` 稳定别名，并在文件头保留 `renamed from:` 注释。报告中给出的对照关系（`WebTransportMgr`=`p086/C0814`、`SocketManager`=`p086/C0809`、`CommandDispatcher`=`p086/C0797`、`KeylogEngine`=`p086/C0804`、`AesCipher`=`p081/C0762` …）即来自这些注释与日志 TAG。

## 3. 重编译

```powershell
# 1) Smali + 资源 → APK（无任何人工改动）
java -jar tools\apktool.jar b -f -o rebuilt\a0dcf711.rebuilt-unsigned.apk apktool_out

# 2) zipalign + 签名（v1/v2/v3）
java -jar tools\uber-apk-signer.jar -a rebuilt\a0dcf711.rebuilt-unsigned.apk --out rebuilt\signed
```

输出：

## 4. 反向验证（四重独立证据）

### 4.1 往返等价：Smali 树逐文件哈希比对

把重编译产物**再次**反编译（`apktool_out_rebuilt/`），与第一次的 Smali 树逐字节比较：

| 指标 | 结果 |
|---|---|
| Smali 文件数 | 5,844 ↔ 5,844（**无缺失、无新增**） |
| 逐字节完全相同 | **5,817 / 5,844（99.54%）** |
| 存在差异 | 27 个文件 |

27 个差异文件的**全部**改动都是“删除等于默认值的静态字段初始值注解”，例如：

```diff
- .field private static final DEBUG:Z = false
+ .field private static final DEBUG:Z
- .field private static GenericTypefaceSetter:sFontFamily:Ljava/lang/Class; = null
+ .field private static GenericTypefaceSetter:sFontFamily:Ljava/lang/Class;
```

这是 smali 汇编器对**冗余默认初始值**的规范化（`false`/`null` 本就是 JVM 默认值），语义完全等价；涉及类均为 androidx 工具类与样本内 3 个 `volatile boolean` 静态标志（`HDStreamService.ث`、`CameraService.ة`、`CompanionIntentService.ؠ`）。

### 4.2 常量级等价：DEX 字符串池

| 指标 | 原始 DEX | 重编译 DEX |
|---|---|---|
| 字符串条数 | 47,591 | 47,590 |
| 新增字符串 | — | **0** |
| 丢失字符串 | — | **1**：`~~R8{"backend":"dex","compilation-mode":"release","has-checksums":false,"min-api":26,"pg-map-id":"6d3f58d","r8-mode":"full","version":"8.1.56"}` |

唯一丢失项是 **R8 编译器的元数据注释串**（并非代码常量）；它同时反证了原始包由 R8 8.1.56 / full mode / min-api 26 构建。

### 4.3 结构级等价：Manifest / 资源 / 原生库 / 资产

| 项 | 原始 | 重编译 | 结论 |
|---|---|---|---|
| `AndroidManifest.xml`（解码后文本） | 32,103 B | 32,103 B | **逐字节相同** |
| `res/` 文件数 | 1,178 | 1,178 | 一致 |
| `res/` 内容 | — | 55 个 PNG 二进制不同 | 逐个像素比对：**尺寸/像素完全一致**（如 1×1、3×3 图标），仅 PNG 容器被 aapt2 重新压缩（67 B → 67 B、77 B → 78 B） |
| `assets/`（含 3 个假更新页 HTML） | 5 文件 / 22,755 B | 5 / 22,755 B | 一致 |
| `lib/`（libadb.so、libnative-guard.so ×2 ABI） | 4 文件 / 8,903,380 B | 4 / 8,903,380 B | 一致（未改动原生库） |
| 类总数 | 5,844 | 5,844 | 一致 |

ZIP 条目名差异仅两类，均可解释：
1. 重编译新增 `META-INF/ANDROIDD.SF/.RSA/MANIFEST.MF`（新签名）；
2. 原始包资源名为混淆形式（`res/0C.xml`、`res/-1.xml`），apktool 依资源表恢复为语义名（`res/anim/abc_fade_in.xml` 等）；条目数变化 1,057 ↔ 1,060 即由此 +3 签名文件导致。

### 4.5 行为级验证：协议独立重实现

- `tools_c2/c2_crypt.py`：纯 Python 实现 AES-128/ECB/PKCS5+Base64，FIPS-197 KAT + 端到端加解密**全部 PASS**（见 `02-通信协议.md` §7）。证明我们对“解密出来的源码”所声明的加密算法/密钥理解正确且可复现。
- `tools_c2/c2_protocol.py`：按反编译源码精确重建 引导 URL / Socket.IO URI / 二进制帧头 / 握手包，输出与源码字符串**逐字符一致**（`30 0000002d {"deviceId":"…","apkId":10068}`）。
- `libnative-guard.so` 的 URL 模板与 Java 侧构造结果在路径与参数顺序上一致（§8 of 02）。

### 4.6 JNI 绑定不一致（反向发现）

`dynsym` 全量 22 项已逐条核对（`scripts/elfsym2.py`）：5 个 `Java_com_example_myapplication_util_N_*` 导出函数，**无 `JNI_OnLoad`、无 `RegisterNatives` 导入**，而 Java 侧类名为 `com.lite.cloudfinder.util.N`（仅 `native void startGuard()`）。

推论链（三条独立证据）：
1. DEX 中不存在 `Lcom/example/myapplication/**` 任何类（字符串池检索为空）；
2. `App.onCreate()` 以 `try { N.startGuard(); } catch (Throwable unused) {}` 包裹；
3. Java 侧无 `buildUrl`/`buildWsUrl` 声明（`util/N.java` 只有 `startGuard`）。

→ 该原生反调试组件在本包中**永不生效**（符号解析失败被静默吞掉），其 URL 模板亦为死代码。重编译后可执行性因此与原包等价。

## 5. 验证结论

| 验证项 | 判定 |
|---|---|
| 类/方法/资源/Manifest 结构完整 | **通过**（5,844 类零缺失，Manifest 逐字节相同） |
| Smali 往返等价 | **通过**（5,817/5,844 逐字节相同；27 处仅默认值注解） |
| 字符串/常量无损 | **通过**（仅丢失 1 条 R8 编译元数据） |
| 协议常量保留 | **通过**（20/20，四源交叉一致） |
| 加密算法可复现 | **通过**（FIPS-197 KAT + E2E） |
| 重编译 APK 签名可安装 | **通过**（zipalign + v2/v3 验签） |
| 原生库 | 未改动，结构/符号/字符串取证一致 |
| 运行时行为（真实 C2 交互） | **未验证**（离线分析，无沙箱服务器；相关结论均标注为静态推断） |

一句话总结：**反编译—重编译的往返在字节码、资源、Manifest、协议常量四个层面均达到等价（唯一差异是可解释的默认值与容器重压缩），且协议模型已被独立实现验证。**
