# 07 · "安卓工程源码"到底包含什么 / 能构建到什么程度

> 结论（一句话）：
> **可构建的工程源码 = `apktool_out/`（5,844 个 .smali + 全资源 + 明文 Manifest），它包含 100% 的 DEX 行为，并且已被证明能重新编译成可安装 APK；`jadx_src/` 是可读的 Java 源码，逻辑全覆盖但"不可直接编译"；原生库只有二进制，没有 C 源码。**
> 你追问的那些机制（防卸载 BACK、takeScreenshot、MediaProjection、WS 帧、AES、163 指令…）**在 smali 工程里逐项落地，43/43 项三源自检全部 OK**（见 §2）。

## 1. 三套产物的定位（别混用）

| 产物 | 是什么 | 能否构建 APK | 覆盖度 | 体积 |
|---|---|---|---|---|
| **`apktool_out/`** | apktool 反编译工程：`smali/`（5,844 文件）+ `res/`（1,178）+ `AndroidManifest.xml`（明文）+ `assets/` + `lib/` + `apktool.yml` | ✅ **可以**：`apktool b` → zipalign → 签名，本机已跑通，产出可安装 APK | **100%**（smali 就是字节码的一一对应，往返比对 5,817/5,844 逐字节相同，27 处仅默认值注解） | 约 120 MB |
| **`jadx_src/`** | jadx 反编译的 Java 源码：3,039 个 `.java`（含 5,844 类 + 内部类），伪装类名映射为 `p000…p120/Cxxxx` | ❌ **不能直接编译**（原因见 §3） | **逻辑全覆盖**：自家代码（`com.lite.cloudfinder.*`）**零反编译失败**；17 处失败全在第三方库 | 19.6 MB |
| `extracted/lib/*` | `libadb.so`（5.1 MB，Termux 构建的 adb）、`libnative-guard.so`（7.5 KB 反调试桩） | 作为预编译 `.so` 参与打包 | — | 8.9 MB |

> 换句话说：**要"能编译出 APK 的安卓工程"，用 `apktool_out/`；要"像 Java 项目那样读代码/审计"，用 `jadx_src/`。**
> 二者是同一份字节码的两个视图，不是两份不同的东西。

## 3. `jadx_src` 为什么"不能直接编译"（诚实清单）

| 障碍 | 具体表现 | 是否影响"读懂逻辑/重建行为" |
|---|---|---|
| 缺构建系统 | 无 `build.gradle(.kts)`、无 `settings.gradle`、无 AGP/SDK 依赖声明 | 否（用 apktool 工程构建） |
| 无 Android SDK / Gradle 缓存 | 本机无 `ANDROID_HOME`、无 `~/.gradle` 缓存，`androidx.*` 依赖离线不可解析 | 否 |
| jadx 合成结构 | `AnonymousClass7`、`C00931`、`this$0`、synthetic accessor、`/* synthetic */` 构造器 | 否 |
| **17 处方法未反编译** | jadx 输出 `throw new UnsupportedOperationException("Method not decompiled: …")` | **否**：对应方法在 smali 中完整存在，只是 Java 视图缺失 |
| 类名/包名被 R8 打散 | `Lڜٟٱڀ/ش;` → `p086/C0814`，字段名 `؋/ؠ/ء` | 否（有 `renamed from:` 注释可回溯） |
| Kotlin 协程状态机 | `invokeSuspend` 系列常出现不可逆的结构（`p018/C0356.handleMessage` 等） | 否 |

**17 处未反编译的分布（全部为第三方库，无一处在本马自家代码）：**

## 4. 一份工程 = 四种"源码"，各有边界

| 纬度 | 是否包含 | 说明 |

| 资源（layout/drawable/values/arsc） | ✅ 完整 | apktool 解码为可编辑 XML/PNG；回编时由 aapt2 重建 `resources.arsc`（Manifest 逐字节一致、1,178 资源、55 张 PNG 仅重压缩） |

## 6. 如果你要"真正能 Gradle 编译的 Java 工程"

严格说需要额外一步（不在本次交付范围内，且工程量大、成功率不保证）：

1. `dex2jar` → `jadx --no-imports` 或 `CFR/Procyon` 交叉反编译，替换 17 处缺失方法；
2. 补齐 `androidx.*` 依赖的精确版本（可从 `META-INF/*.version` 文件读出，例如 `androidx.core_core.version`），或改用 `libs/*.jar`；
3. 把 R8 打散的包名（`p000–p120`）保持为独立 package（可编译，无需还原原名）；
4. 手工修复合成访问器、协程状态机、`switch` on 常量名（jadx 已用 `/* 53 */` 注释保留数值）；
5. 用 aapt2 链接 `res/` 与 `AndroidManifest.xml`，再 `d8` 生成 dex。

**但如果你只是想要"源码 + 能编译出等价 APK"**——`apktool_out/` 已经满足，而且是**字节级可验证**的等价（见报告 03）。

## 7. 澄清："没有的东西"≠"反编译不准/缺内容"

我此前说的"没有"其实混了三类完全不同性质的东西，容易被读成"反推出来的源码不准确、少东西"。拆开说：

### 类别 A：**本来就不在 APK 里**（与反编译质量无关）

| 缺的东西 | 为什么没有 | 想要它需要做什么 |
|---|---|---|
| 原生库 **C/C++ 源码** | APK 只装编译好的 `.so`（aarch64 机器码）。源码从未进入安装包，任何反编译都不可能在包里"找到"它 | 反汇编/反编译机器码（Ghidra/IDA），得到的是**伪代码**而非原始源码；本项目只做了符号表+字符串+导入表取证 |
| **服务端源码** | C2 服务器是独立部署的另一套程序，客户端包里只有"调用方式" | 只能按客户端契约反推（报告 04）+ 自己写参照实现（`mock_c2_server.py`）；真实服务端实现细节**原理上不可从客户端完全确定** |
| **签名私钥** | 签名机制的本质：包内只有证书/公钥，私钥在作者手里 | 无法获取；重编译改用本地 debug key（客户端不做证书固定，不影响行为验证） |

### 类别 B：**R8 优化后不可逆**（任何工具都还原不了，不是我们的缺口）

- 原始**变量名/参数名/注释/代码排版**：R8 已把它们删掉，反编译只能生成 `v0/v1`、`؋/ؠ`、`pNNN` 这类占位名；
- 原始**源码文件划分**（哪些类原本在同一个 `.java` 里）：同样已消失。

→ 这一类是"信息在编译期就丢了"，**任何"反编译得多准"都无法恢复**。

### 类别 C：**视图形态差异**（内容在，只是不能 `javac`）

| 视图 | 内容是否完整 | 能否直接编译 |
|---|---|---|
| `apktool_out/smali`（推荐） | **100%**：5,844/5,844 类、指令级一一对应 | ✅ 能（`build.ps1` 已验证） |
| `jadx_src` Java | **逻辑完整**（自家业务零缺口），但 17 处方法只有 `UnsupportedOperationException` 占位 | ❌ 不能（缺 Gradle/依赖/合成结构） |

### 那么"准确"到什么程度？——用数字说话（全部可复跑）

| 维度 | 结果 | 复跑命令 |
|---|---|---|
| 类数 | 5,844 ↔ 5,844，缺失 0、多出 0 | `verify_rebuild.py` |
| 方法引用集合（method_ids 权威，含外部引用） | 6,484 ↔ 6,484，**差异 0** | `verify_rebuild.py` |
| 字符串池 | 47,591 ↔ 47,590，唯一丢失是一条 R8 编译元数据串 | `verify_rebuild.py` |
| 协议常量 | 23/23 全在 | `verify_rebuild.py` |
| Manifest | 解码后 32,103 B **逐字节相同** | `verify_rebuild.py` / 手工 diff |
| 资源 | 1,178 文件数量一致；55 张 PNG 仅重压缩（像素级相同） | `pngcmp`（历史脚本） |
| smali 往返 | 5,844 文件，**5,817 逐字节相同**；27 个不同的文件共 **118 行差异，全部是 `.field … = false/null` 默认值注解**（0 处指令差异、0 处方法签名差异） | `smalidiff.py` |
| 机制覆盖 | 43/43（smali / java / rebuilt-dex 三源齐全） | `coverage_check.py` |
| 加密可复现 | FIPS-197 KAT + 端到端全 PASS | `tools_c2/c2_crypt.py selftest` |

**结论**：`apktool_out/` 这份"反推源码"在**内容上不缺少、在行为上可验证等价**；所谓"缺"的部分，要么是包里根本没有（A 类）、要么是编译期被抹掉（B 类）、要么只是 Java 视图不可编译（C 类）。**唯一需要额外投入的是 C 类里"想要 Gradle 工程"这条路线**，与准确性无关，只关系到"用哪种形态再编译"。
